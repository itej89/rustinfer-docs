OCP MX v1.1.0 audit

Audit of 2026-11-14 on origin/main 8c7d47e, against the requirements, after PRs #55 (6a18042),

53 (8d58ad6) and #49 (8c7d47e: Quark and compressed-tensors MXFP4

checkpoint import, checkpoint KV scales) merged. None of them changes reference/mx.rs, mir/src/mx.rs or their tests, so MX-R1 to MX-R13 stand as read; the checkpoint path is new (see below). History: first audited 2026-11-13 on ccf02b3, re-audited the same day on b99720a after PR #48 (KV dtypes, with MXFP4 KV).

Method. Read the specification text (pdftotext -layout of specs/number-formats/ocp-mx-v1.1.0.pdf), §3 to §6.3. Read origin/main at b99720a: crates/rustinfer-target/src/reference/mx.rs, crates/rustinfer-mir/src/dtype.rs, crates/rustinfer-mir/src/mx.rs, the tests crates/rustinfer-target/tests/mx.rs and crates/rustinfer-mir/tests/mx.rs, the golden file crates/rustinfer-target/tests/data/mx_golden.txt and its generator crates/rustinfer-target/tests/mx_golden/mod.rs, and the MXFP4 KV path of PR #48 (crates/rustinfer-mir/src/kv.rs, crates/rustinfer-target/src/reference/kv.rs, their tests). Worked the Equation 4 thresholds by hand: for E2M1 (one mantissa bit) a significand rounds up to 2 exactly from 1.75, a tie that goes to the even 10.0; for E4M3 1.8125 is a tie that goes to the even 1.75, anything above it and below 1.9375 rounds to 1.875, and 1.9375 itself carries to 2. Read SRS v0.4.3 on origin/main and the file lists of open PRs

44 and #49. No tests were run.

Test tags. The E2M1 decode, UE8M0 decode, fp4x2 packing and storage tests carry Verifies RI-MIR-003. The conversion tests and the golden file carry Groundwork for RI-MIR-012, and the mx encoding checks Groundwork for RI-MIR-011: by the rule of docs/testing.md those clauses count as not implemented until their build-time and kernel parts land (#36, #38). The module header of tests/mx.rs says so (:5-10). The assertions themselves bind the CPU reference and are the evidence below.

The independent check. The golden generator shares no code with reference/mx.rs and uses no floating-point arithmetic: it decomposes each f32 from its bits, builds the E2M1 and E4M3 grids from their bit fields (mx_golden/mod.rs:53-94), and applies §6.3 with Equation 4 on integers (:1-18). test_golden_file_is_the_independent_generator_output (tests/mx.rs:306) requires the committed file to be its output, and test_golden_blocks_quantize_bit_exactly (tests/mx.rs:320) requires the reference to reproduce all 51 blocks (25 E2M1, 26 E4M3) bit for bit.

The mx matmul reference (mx.rs:486-507) computes the §6.2 general dot product by dequantizing the weight and accumulating in f32; the dot products are outside the scope.

Outside the scope, noted

  • The reference also converts with E4M3 elements (MXFP8, MxElement::E4m3). MXFP8 is not in the Scope phrase. If it were claimed, §5.3.1 would require both the SAT and NONSAT FP8 modes; rustinfer has the saturating mode only, and OCP-OFP8 is scoped to it (OFP8-1, out of scope since PR #50).
  • How a Quark or compressed-tensors quantization_config is read is the QUARK and CT standards; the MX side of that import is below.

MXFP4 checkpoint import (PR #49, merged 8c7d47e)

The frontend now imports dense Quark and compressed-tensors MXFP4 checkpoints (issue #35) into the MX types this audit checks, rather than converting them, so the §6.3 conversion is not exercised: the stored bytes are taken as E2M1 codes and UE8M0 scales.

  • Each MXFP4 projection becomes an fp4x2 weight of its logical shape with the mx encoding, block size MX_BLOCK_SIZE (32), along the innermost axis, with ue8m0 scales (crates/rustinfer-frontend/src/dtypes.rs:120-139, src/mapping.rs:268-295); the packed data must be U8 with the innermost axis halved, or F4 in values, and the scales U8 or F8_E8M0 with the block axis divided by 32, else refused naming the tensor (mapping.rs:297-322, axis check :159-161). The Model IR's own mx check (MX-R2) still applies.
  • The weight's config.json fields must name MXFP4 exactly as MX-R2 does: Quark fp4, per_group, group_size 32, ch_axis −1, scale_format e8m0 (src/quant/quark.rs:110-139); compressed-tensors 4-bit float weights in groups of 32 with uint8 scales (src/quant/ct.rs:160-189).
  • Nibble order: low nibble first, the even element in bits 3..0, as RI-MIR-003 states and the CPU reference packs (reference/mx.rs:305-339). OI-014 is closed by SRS v0.4.8 (docs/SRS-RI-v0.1.md:27, :2091-2100): Quark's Pack_fp4.pack and Pack_fp4.unpack fix that order. The frontend tests decode each fixture's bytes through a line-for-line port of Pack_fp4.unpack and through the CPU reference mx_dequantize, and require the values written, bit for bit, for both producers and four families (check_mx_weights, crates/rustinfer-frontend/tests/mxfp4.rs:71-104; test_quark_fixture_of_each_family_lowers_to_mx_weights :111, Verifies RI-MIR-003; test_compressed_tensors_fixture_of_each_family_lowers_to_mx_weights :125). test_quark_compressed_tensors_convention_hand_built (crates/rustinfer-target/tests/mx.rs:535) still decodes a hand-built tensor. No real checkpoint was decoded.
  • Bad shapes and dtypes are refused naming the tensor: test_bad_mx_tensors_are_refused_naming_the_tensor (tests/mxfp4.rs:587), test_packed_u8_shape_mismatch_is_refused_naming_the_tensor (tests/mxfp4_review.rs:162); F4 and F8_E8M0 headers lower like U8 (tests/mxfp4.rs:716).

KV scales. The checkpoint KV scales of PR #49 are fp8 per-layer scales, not MX: apply_kv_scales fills only an fp8 KV group's KvScales and leaves a group without fp8_scales untouched (crates/rustinfer-frontend/src/kv_scales.rs:102-121). An MXFP4 KV group still computes its UE8M0 block scales at the cache write (below); test_without_scales_or_fp8_the_geometry_is_unchanged (crates/rustinfer-frontend/tests/mxfp4_kv_fp8.rs:102) checks that a --kv-dtype mxfp4 geometry records no fp8 scales from a checkpoint that has them. No MX item is affected.

MXFP4 KV cache (PR #48, merged e218b8a)

  • The Model IR gives an MXFP4 KV group fp4x2 storage with the mx encoding along head_dim and ue8m0 scales (crates/rustinfer-mir/src/kv.rs:31-45, :52-56), and refuses a head_dim not a multiple of 32 (:147-150; crates/rustinfer-mir/tests/kv_dtypes.rs:122).
  • The CPU reference cache write applies §6.3 per 32-value block with E2M1 elements through mx_quantize_block (crates/rustinfer-target/src/reference/kv.rs:287-298), stores the packed values then the UE8M0 scales, and reads back 2^s × E2M1(code) with mx_dequantize_block (:353). Being the same function as the oracle, it inherits MX-R1 to MX-R13. test_cached_k_and_v_equal_the_oracle_conversion_bit_exactly (crates/rustinfer-target/tests/kv.rs:212) and test_attention_over_quantized_kv_equals_attention_over_the_oracle_values (:290), both Groundwork for RI-KVC-008, RI-MIR-012, check it.

Result

Every in-scope item conforms in the Model IR and the CPU reference, the oracle the other targets are checked against; since PR #48 the MXFP4 KV CPU reference applies it, and since PR #49 (8c7d47e) checkpoint MXFP4 weights import into the same fp4x2, ue8m0 and mx types, low nibble first (OI-014 closed, SRS v0.4.8). The paths that must apply the same rule at build time (MX-1), in the GPU KV kernels (MX-2) and in kernels (MX-3) are not on origin/main. Partial, for the R1 coverage, not for any wrong value.
