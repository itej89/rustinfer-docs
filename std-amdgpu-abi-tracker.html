AMDGPU code object V5 tracker

Gaps found by the audit of 2026-11-13, re-audited on 2026-11-14 against main 81fbcba after PRs #58 (merge 53dac5b, issue #12) and #44 (merge 38f2f60, issue #8) merged. Hardware evidence: the GPU tests #45 and #59 passed on an MI350X (gfx950) under ROCm 10.1 (10.1.0-3) on 2026-11-15 (UTC), results in #54; gfx942 has not been run (#61). ABI-5 was found on 2026-11-15 against b057ef5, after SRS v0.4.11 extended the scope to the cache-policy bits.

id gap required by status notes
ABI-1 No code object on main: no ELF header, e_flags, ET_DYN link or V5 version (AB-R1, AB-R3 to AB-R8, AB-R15) Header, AMDGPU ELF Header e_flags for Code Object V4 and V5, Sections, Module Flags Fixed 2026-11-14 38f2f60 PR #44 (issue #8). Triple amdgcn-amd-amdhsa and code-object version 500 through the amdhsa_code_object_version module flag (crates/rustinfer-kc/src/mlir/llvm.rs:28, :32, :268-287), PIC, no forced features (:241-265), ld.lld -shared --no-undefined in-process (:348-358, src/mlir/lld_shim.cpp:47-63). Tests (Groundwork for RI-KC-008 and RI-KC-003): test_trivial_module_compiles_in_process_byte_identically (crates/rustinfer-kc/tests/amd_lowering.rs:403, ET_DYN, EM_AMDGPU), test_code_object_elf_flags_name_the_architecture (:434, EF_AMDGPU_MACH, XNACK and SRAMECC ANY, EI_ABIVERSION 3)
ABI-2 Some fields of the objects the kernel compiler writes have no test: amdhsa.target, the .kd symbol's STT_OBJECT type and 64-byte alignment, the <name> STT_FUNC entry symbol, the descriptor's KERNEL_CODE_ENTRY_BYTE_OFFSET (256-byte aligned entry) and reserved fields, and the dynamic sections (AB-R8, AB-R10, AB-R12, AB-R14) Sections; Symbols; Code Object V5 Metadata; Code Object V3 Kernel Descriptor Open Narrowed by PR #44 (38f2f60), which added test_code_object_header_is_hsa_dynamic_with_no_entry (amd_lowering.rs:543, EI_OSABI 64, e_entry 0), test_code_object_metadata_note_lists_the_kernel (:560, the NT_AMDGPU_METADATA note, amdhsa.version [1, 2], .symbol, .kernarg_segment_size, .group_segment_fixed_size, .vgpr_count, .sgpr_count) and test_kernel_descriptor_symbol_holds_the_declared_lds (:585, a 64-byte .kd in .rodata whose GROUP_SEGMENT_FIXED_SIZE and KERNARG_SIZE match the metadata), all Groundwork for RI-KC-003. The test reads the symbol's info byte (crates/rustinfer-kc/tests/code_object/mod.rs:116) but asserts neither type nor alignment. On main the ROCm target's reader refuses an object without amdhsa.target (crates/rustinfer-target-rocm/src/code_object/metadata.rs:22-25) but does not compare it; amdhsa.target is asserted only for the test writer's objects (crates/rustinfer-target-rocm/tests/code_object.rs:38). The fields left are written by LLVM and lld, and the gfx950 objects loaded and ran exactly (#45), so they are likely right; a back-end default change would still pass unnoticed
ABI-3 No code object had been loaded by the HIP module loader (AB-R4, AB-R10); now only gfx942 remains Header ("The AMD HSA runtime loader requires a ET_DYN code object"); Symbols Open (gfx942, #61); gfx950 verified 2026-11-15 (#45, #59, results in #54) gfx950, MI350X, ROCm 10.1 (10.1.0-3): #45 loaded the kernel compiler's objects with hipModuleLoadData and hipModuleGetFunction and ran them, 4 passed, every line max_abs_err=0; #59 loaded the in-process V5 objects of the ROCm target's tests (module_load_and_launch, 11 passed), whose loaded image is byte-identical to llvm-mc plus ld.lld -shared (test_writer_matches_llvm_byte_for_byte, crates/rustinfer-target-rocm/tests/code_object_golden.rs:125, in CI). #45 ran at 821a57e, the PR #44 head before its rebase onto #58's target; on main the same objects load through RocmTarget (tests/gpu_code_objects.rs:1-8), so #61 also asks for a gfx950 re-run of #45 on main. Open until #61 reports gfx942 (MI300X)
ABI-4 No metadata reader: the LDS and register needs of each kernel were not read, so RI-ROC-004's check before the first launch could not be made (AB-R13) Code Object V3 Metadata, kernel table (.group_segment_fixed_size, .sgpr_count, .vgpr_count, .agpr_count) Fixed 2026-11-14 53dac5b PR #58 (issue #12). A bounded reader of the ELF header, the PT_NOTE metadata note and its MessagePack map (crates/rustinfer-target-rocm/src/code_object/mod.rs:102-127, elf.rs:96-133, :185-198, metadata.rs:14-64) refuses anything but ELF64 LSB, ELFOSABI_AMDGPU_HSA, V5, ET_DYN, EM_AMDGPU, amdhsa.version [1, 2], and a kernel lacking a required key; check_code_object (src/device/kernels.rs:102-120) checks processor, XNACK, SRAMECC, LDS, work-group, wavefront and register limits (src/resources.rs:63-81) before HIP loads the object. Tests: tests/code_object.rs:30, :98, :142 (Verifies RI-ROC-004), tests/resources.rs:56 and following (Verifies RI-ROC-004), tests/architecture.rs:125, :143 (Verifies RI-ROC-003). On gfx950 hardware #59 refused a kernel needing 163844 LDS bytes against 163840 and launched one at the limit; gfx942 (65536) is #61. .kernarg_segment_align is not read; nothing needs it
ABI-5 No cache-policy bits: nothing maps an abstract hint to sc0, sc1, nt (gfx942, gfx950) or to the GFX125x temporal hint and scope, and the description reports no hint (AB-R16) AMDGPU Load-Visible Implementation, AMDGPU Store-Available Implementation; Memory Model GFX942; Memory Model GFX125x; SRS RI-KC-015 (iii), RI-KC-016 (h) Open Found 2026-11-15 on b057ef5, after SRS v0.4.11 (PR #65) extended the scope. Planned in #64 (open, R1): the hint field, the cache-hints pass, and the lowering to SC1, SC0 and NT through the ROCDL gfx942_cache_policy attribute; acceptance: streamed-weight loads carry NT on gfx942 and gfx950, reused tiles do not, and a target without hints gets an unchanged module. The GFX125x values (th:TH_LOAD_NT, scope:SCOPE_*) are for the gfx1250 target, outside R1
