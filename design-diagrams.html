Key crate external library dependencies point down

rustinfer-target does not depend on rustinfer-artifact: the conversion between a target KernelBinary and the artifact's kernels entry (RI-ART-013) sits on the two sides that already depend on both. The build side is rustinfer_compiler::kernel_to_artifact (GC --> ART, GC --> TGT), the load side rustinfer_runtime::kernel_from_artifact (RT --> ART, RT --> TGT) (#27). The binary format both name is rustinfer_core::kernel::BinaryFormat, in the lowest crate both depend on: it is not Model IR vocabulary, so it does not belong in rustinfer-mir.

rustinfer-target-rocm reaches the HIP runtime only at run time: with the rocm feature it opens libamdhip64.so.7 with dlopen from the system library directories (ADR-003 amendment of 2026-11-14), so no build links against ROCm and the dashed edge is a run-time one.

rustinfer-core, rustinfer-cli, rustinfer-mir, rustinfer-artifact, rustinfer-planner, rustinfer-target, rustinfer-target-rocm and rustinfer-sluice carry behaviour, and rustinfer-compiler and rustinfer-runtime carry the kernel conversion; every other crate has its error type and public surface so the dependency graph is fixed from the first commit (G22: logical dependencies made physical). rustinfer-mir depends on serde and serde_json for the canonical JSON form; rustinfer-artifact on the same plus sha2 for the content hash (external, not drawn). rustinfer-planner carries behaviour from PR #15 (topology model, placement types, single-device planner) and depends on rustinfer-mir for the document it fills and on serde and serde_json for the topology and placement sections; it depends on no target or artifact crate.

rustinfer-frontend depends on regex (external, not drawn) for the re: and glob entries of an MXFP4 checkpoint's exclusion list (#35, RI-FE-006): linear-time matching under a compiled-size limit, so an untrusted pattern cannot cost more than its bound (RI-SEC-003).

rustinfer-kc carries behaviour from PR #7 (the Kernel IR dialect, the typed builder, the MLIR link) and depends on tracing; from #9 it depends on rustinfer-target for the CPU reference operators and conversions its generators validate against (RI-KC-007) and on rustinfer-mir for the operator a generator implements (OpKind); with its mlir feature it links MLIR and LLVM 23 statically through melior and mlir-sys (ADR-007), the external node drawn dashed above. From #8 it also links lld statically (liblldELF.a, liblldCommon.a from liblld-23-dev) to emit AMD code objects in-process (RI-KC-008). rustinfer-target-rocm depends on rustinfer-kc (with mlir) only under its rocm-test feature, for the hardware harness that loads those code objects through HIP.

From #64 the Kernel IR (rustinfer-kir: the dialect, the builder, the recorded program, the capability description, the compiler settings and the host buffers, on rustinfer-target for their conversions) and the generators (rustinfer-generators) are their own crates (RI-KC-014). A generator depends on the Kernel IR, rustinfer-core and rustinfer-mir only, so it cannot reach the lowering, a target or the CPU reference; the kernel compiler's passes, lowering, catalog and tuner depend on both and re-export them (rustinfer_kc::generators, rustinfer_kc::KernelBuilder). rustinfer-kc's tests/generator_crate.rs checks the generator crate's dependencies with cargo metadata.

The command is the composition root of the target registry (ADR-003, RI-TGT-004): it depends on every backend crate and registers each crate's one TargetEntry; the compiler, planner and runtime see only rustinfer-target. The four backend crates implement Target with an empty catalog and no device until their hardware issues land (#12 and the RISC-V milestones).

rustinfer-sluice (PR #18) is the weight streamer of SRS §3.2.22: it depends on rustinfer-artifact for the weight manifest and the checkpoint identity, on rustinfer-target for the Device it fills, on rustinfer-mir for DType, and on sha2 for the hashes; the safetensors header is read by the one reader both it and the frontend use, rustinfer_artifact::safetensors (#27), which lives in the artifact crate because the safetensors shard is the checkpoint format the manifest references and its header hash is the file identity; it never sees the Model IR document or the Plan. The runtime (#13) and the run command (#14) are its callers; the edge from the runtime is drawn for them. From #11 the command links it: build opens the compiled weight manifest with Sluice::open exactly as a load will, so an artifact no load could stream is never written, and --hash-weights takes each tensor's digest from Sluice::digest_weights (RI-ART-005). The checkpoint files it reads are its external boundary (SWG-001 §8.7, docs/entry-points.md).

Model IR (rustinfer-mir, SRS §3.2.3, PR #3)

The typed SSA graph every frontend lowers to and every backend consumes. Data types are plain structs with public fields and derive Serialize/Deserialize; behaviour lives in Document (validation, canonical JSON), the operator registry (a static table, one row per operator) and the bounded reader. Every type is Send + Sync by construction (no interior mutability).

Sluice, the weight streamer (rustinfer-sluice, SRS §3.2.22, PR #18)

Sluice's only description of the model is the weight manifest (RI-ART-005); it never sees the Model IR or the Plan. Sluice::open canonicalises the checkpoint root, observes the checkpoint identity (config.json hash, every recorded shard's size and header hash) and refuses on the first difference (RI-ART-012), parses the safetensors header of every shard the rank needs under named bounds (RI-SEC-003), and checks dtype, shape and byte range of every needed tensor against that header before any tensor byte is read (RI-WST-005). Sluice::load then streams each needed weight by byte range through a staging pool bounded by RUSTINFER_STAGING_BYTES (RI-WST-002), copies it to the device and runs the manifest's transform on the device as runs of copy_on_device (RI-WST-003; the graph compiler's recorded launches replace the runs from #10), with reads, copies and transforms on three threads joined by bounded channels (RI-WST-004). verify_weights is the separate full read that --verify-weights asks for: it compares every needed tensor with the SHA-256 the manifest records for it (RI-ART-005), or with externally given digests when the caller passes them, and refuses the first weight with no expected digest.

MXFP4 (#39, RI-WST-003): an imported mx weight becomes two WeightPlans, its packed data (Part::Data) and its scale tensor (Part::Scale), each checked against its own header and streamed by its own byte range through the same pipeline and staging pool; slices count storage units, so fp4x2 moves two values per byte. A weight whose transform is dequantize_mx or quantize_mx becomes a Conversion instead, run after the pipeline in batches of whole slabs under the same budget through the MX oracle of the CPU reference; any other device is refused (TransformUnavailable) until

38 brings its kernels. verify_weights checks one digest per tensor, the

scale keyed <weight>#scale. A U8 [out, in/2] header (raw bytes, StoredDtype::U8) matches an fp4x2 [out, in] entry. A scale range that a needed plain entry also covers (the scale as its own Model IR weight) streams once as that weight: a streamed mx weight then shares its buffer (aliases), and a conversion copies its scales back from it (Conversion::scale_weight).

Frontend (rustinfer-frontend, SRS §3.2.2, PR #6)

A Hugging Face checkpoint directory lowered into one Model IR document with prefill and decode over one weight set, the weight manifest and the checkpoint identity. Two external boundaries (SWG-001 §8.7): config.json and the safetensors header of every shard, both untrusted, both parsed under Limits into typed structures before anything is derived from them. No weight byte is read (RI-FE-004). Everything is a pure function of the directory contents; there is no shared state.

The crate is split at the architecture seam (src/arch/): the generic modules (lowering, config, fields, safetensors, mapping, limits, error) mention no model family; everything that varies per architecture sits behind the crate-internal Architecture trait, selected by model_type through the registry of arch/mod.rs. The LLaMA family (llama, mistral, qwen2, qwen3) is the one architecture of R1, under src/arch/llama/; a minimal test-only architecture proves the seam. Adding an architecture is one directory plus one registry line (RI-FE-005 is the first real one).

Checkpoint quantization (#35, RI-FE-006). quantization_config is read first and generically by src/quant/ into a Quantization: none, or an Mxfp4Checkpoint from AMD Quark or compressed-tensors, its exclusion list (Patterns: exact names, fnmatch globs, re: patterns), its calibrated activation format and its KV quantization. An architecture says which of its tensors may be MXFP4 (ExpectedTensor::with_mx_axis; the LLaMA family marks its seven projections along their input features); the mapping turns each such tensor that the list does not exclude into an MxWeight (packed data and ue8m0 scales), and TensorDtypes::weights gives the document its fp4x2 weight with the mx encoding and its scale weight.

Lowering, per layer i (the LLaMA architecture's operator sequence of prefill and decode; tensor names are layers.i.<role>, node names layers.i.<op>): rmsnorm(h, input_layernorm) → matmul q, k, v (transpose_b, bias when the family has one) → rmsnorm q and k by q_norm/k_norm with group = head_dim (qwen3 only, #26) → rope(q, k, positions) → kv_cache_write(k_rot, v, slot_mapping) into the one KV group main → attention_prefill(q_rot, k_rot, v) in prefill or attention_decode_paged(q_rot, block_table, seq_lens) in decode → matmul o → residual_add → rmsnorm(post_attention_layernorm) → matmul gate and up → silu_and_mul(gate, up) → matmul down → residual_add. A projection stored as MXFP4 is read through layers.i.<role>_proj_dequant: dequantize(data, scales) → layers.i.<role>_proj_weight in the compute dtype right before its matmul (#35). Kernel IR and the MLIR link (rustinfer-kc, SRS §3.2.5, ADR-005, ADR-007, PR #7)

The tile-level Kernel IR is the kir MLIR dialect. Its operation set is a Rust table (OpSpec), from which the crate generates the IRDL definition that MLIR loads at context creation and the verifier it runs on every kernel; the builder emits the generic textual form MLIR itself prints, so the text a generator produces (RI-KC-001) is byte-identical to the text MLIR prints after parsing it (the canonical form kept beside each binary, RI-ART-013). Tiles are values (vector<RxCxT>, the register space); buffers are memref values in the global (1) or shared (3) memory space; structured control flow is scf.for; scalars are arith. No operation of the dialect produces a thread, lane or wave identity (RI-KC-002); kir.program_id and kir.num_programs name the work group's place in the launch grid (#64). The AMD lowering reads the text back into its Program, distributes it over the lanes of a work group (simt::distribute, a LaneProgram the host simulator also runs) and prints the lane program as a gpu.module. KernelContext is the only module that touches MLIR (crates/rustinfer-kc/src/mlir/, the unsafe module of ADR-007); it exists only with the mlir feature.

The lowering of R1 rewrites each kir operation in place on the MLIR IR (kir.tile_load → vector.load or vector.maskedload, kir.tile_store → vector.store or vector.maskedstore, kir.make_mask → vector.create_mask, kir.mma → vector.contract, kir.reduce → vector.multi_reduction, kir.barrier → nothing for Flavor::Host, gpu.barrier for the ROCDL flavours) and then runs the flavour's pipeline. For Flavor::RocdlGfx942 and Flavor::RocdlGfx950 (#8) a preparation step (mlir/rocdl) runs between the two: vector.contract becomes a call to a generated helper that runs the Mfma chosen by AmdArch::mfma (bf16 on both, FNUZ fp8 on gfx942, OCP fp8 on gfx950; any other pair is Unsupported naming the architecture and the dtype), a masked global load or store becomes bounded amdgpu.raw_buffer_* accesses, two-dimensional accesses and reductions become one per row, and the kernel moves into gpu.module @kir_kernels as a gpu.func whose shared buffers are work-group (LDS) attributions. KernelContext::compile then translates the gpu.module, runs the LLVM AMDGPU back end through the C API and links the object with lld as a library into a CodeObject (RI-KC-008); CodeObject::disassemble reads it back with the LLVM MC disassembler.

The generators (#9, rustinfer_kc::generators) emit every kernel through KernelBuilder, which records a Program and prints it with MLIR's own value naming, so the text is a fixed point of verify. A Generator declares its ParameterSpace (key axes: the problem, the catalog key; tuning axes: the kernel's choices), says which points run on which Capabilities (never an architecture: ADR-011), takes its tile sizes as CompilerSettings, and validation builds a Case on the CPU reference operator; interpret runs the recorded program on HostBuffers, and compare checks every output within the Tolerance of its dtype (rustinfer_kc::tolerance, RI-KC-007). Gemm is the first generator (9a); the rest follow in the stacked PRs of #9.

The autotuner (#9, 9c; rustinfer_kc::tune) searches the setting axes of each key: a Tuner generates each variant for the device's Capabilities, compiles it with a KernelCompiler (MlirCompiler: KernelContext::compile), loads, runs and times it on a TuningDevice (the ROCm device in rustinfer tune, a mock in the tests), checks the outputs against the CPU reference with validation::check_case and keeps the fastest correct one as a CatalogEntry of the target's Catalog (rustinfer_kc::catalog, docs/api/catalog.md).

Runtime (rustinfer-runtime, SRS §3.2.11 to §3.2.14, #13)

The executor of R1 (docs/api/executor.md). Engine::load checks the artifact and the configuration, places the document with the planner, allocates the Memory once and resolves each function's BucketLaunches; Engine::step runs one iteration of the static batch. The engine and its Memory belong to one thread; the Executor shares only Shared (the request queue and the response board) with the API threads. Every launch is bound from its Plan entry's args (Resolver::bind); the constants and KV scales the launches read are uploaded once (Constants), and a device sampler's uniform draws come from Draws. Executor (RI-RT-003, RI-RT-008, RI-RT-010, RI-SCH-003; #13) — R1

The R1 executor runs an engine on one thread, rustinfer-executor, which owns the engine and every device buffer (arena, KV pools, slot table, weights); enqueue and await_responses are called from any number of threads. The threads share exactly three things:

shared state primitive held for lock order
request_queue (Shared::requests, bounded by queue_capacity) Mutex<VecDeque<Queued>> + Condvar requests_ready one push (enqueue), one pop (admission), or the idle wait with a timeout (RUNTIME_IDLE_WAIT_MS) never held with responses
responses (Shared::responses) Mutex<VecDeque<Response>> + Condvar responses_ready one push (a finished request) or one drain (await_responses, with its timeout) never held with request_queue
request ids, stop flag AtomicU64, AtomicBool — —

No lock is held across a launch, a device copy or a wait on the other lock: a request is checked before the queue lock is taken, and the engine's state (batch, block pools, slot table image, staging) is the executor thread's alone, with no lock at all. One iteration runs at a time on the engine's one compute stream over its own arena (RI-RT-008); the readback runs on a second stream after an event. A poisoned mutex is taken over, since every critical section leaves its deque whole. A failed iteration is handled on the executor thread: its batch is answered as failed and its blocks freed there (RI-RT-006). shutdown sets the stop flag, wakes the thread, which serves what is queued and returns the engine.

The profiler (RI-OBS-007, #127) adds no shared state: the Profile (span buffer, events, counters) is a field of the engine, written only by the executor thread, one writer, no lock. Its buffer and events are created at load; an iteration writes spans into the preallocated buffer and records events on the compute stream without waiting; the device durations are read after the iteration's readback, so the profiler adds no host synchronisation, and a reader takes the profile from the engine after shutdown returns it (or from an engine stepped by its owner).

ROCm device (RI-ROC-001, RI-RT-008, RI-RT-010, RI-CON-002) — R1, #12

The ROCm device keeps the CPU device's contract with real streams. HIP work is asynchronous: a launch, a device copy, record and wait enqueue on a stream and return. One stream per iteration (RI-RT-008): the executor creates a stream per concurrent iteration and gives each its own arena region; the device never shares a stream between two callers on its own. Ordering between streams is by events on the device (record then wait, no host). The host blocks only in the counted calls (synchronize, synchronize_event, the readback of copy_to_host, and an upload copy_to_device, counted as blocking_uploads), in a replay segment marked host-synchronising (which calls synchronize), and in free, where hipFree synchronises the device implicitly (HIP reference); buffers are freed outside the decode path. Host-to-device and device-to-host copies from a Rust slice use hipMemcpyWithStream, which is synchronous with the host by contract (HIP reference: an async copy and a stream sync), so the host slice need not outlive the call; that is why an upload is a counted host sync (RI-RT-010) and the decode path must perform none. Copies from and into a host staging buffer (copy_from_staging, copy_to_staging, #93) are hipMemcpyAsync from page-locked memory: they return before the copy completes and the buffer's last-use event guards its reuse. An imported mx weight's scale tensor is one more plan in the same reader → copier → transformer order, taking chunks from the same pool, so data and scales share the staging budget by construction. The MX conversions (dequantize_mx, quantize_mx) run on the main thread after the three stages have joined and the streams have drained, one batch at a time, each batch's host buffers counted against the whole budget (StagingTooSmall at open if one slab cannot fit); the pipeline's chunks are free by then, so the two never hold host memory at once and staging_peak_bytes is the larger of the two peaks.

Kernel compiler: one MLIR context per compilation thread (RI-KC-008, RI-KC-011, ADR-007) — R1

An MLIR context owns every type, attribute and operation created through it and is not safe to mutate from two threads. KernelContext therefore holds raw pointers (so it is !Send + !Sync by construction), is created by the thread that compiles, and is dropped by that thread; MLIR's internal thread pool is disabled at creation so a pass pipeline never spawns threads of its own and two compilations of the same text on two threads produce byte-identical output. Autotuner: one kernel at a time on one device (RI-KC-006, RI-CLI-007) — R1

rustinfer tune runs one Tuner on one thread. The tuner holds the TuningDevice by &mut for the whole run and the device uses one stream, so no two variants ever run or are timed at once (a timing measures one kernel alone). Each variant is compiled on the tuner's thread with its own KernelContext (above), then loaded, run once on fresh device copies of the validation buffers, synchronised and copied back, and timed after KC_TUNE_WARMUP_LAUNCHES untimed launches (#146): N and 2N launches are captured into two HIP graphs on the tuner's stream, and each graph is replayed between two events behind a device-side gate. The tune thread closes the stream (hipStreamWaitValue32 on a pinned word), queues the start event, the graph and the end event, then opens it with a host store, so the device runs the three back to back without the host. A watchdog thread per gate opens it after KC_TUNE_GATE_WATCHDOG_MS if the tune thread has not (a HIP call blocked on the closed stream), and dropping the gate opens it on every error path, so the stream cannot stay closed. Where the device refuses the gate the graphs are timed ungated; where it refuses the capture each launch is timed between its own two events. Both graphs are destroyed after the sample and device buffers are freed before the next variant. There is no shared mutable state, no lock and no worker pool; a failed variant leaves nothing behind but its rejection record. Each variant is unloaded after its timing, and both of its timing events are destroyed. The catalog is written after every key through a temporary file that is flushed (fsync) and renamed over the output, so an interrupted run leaves the last complete key's catalog and --resume continues from it.
