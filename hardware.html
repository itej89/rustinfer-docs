Hardware

Read from SRS §2.4, §3.2.8 to §3.2.10, ADR-003, docs/planning/datacenter-device-inventory.md, crates/rustinfer-target/ and the four backend crates at commit f039b4d; the targets table is read from the code since GitHub PR #21 (2026-11-12, issue #5), the device tables from the inventory. The inventory's scope statement: AMD and the open-standard and RISC-V ecosystem around it; NVIDIA parts are out of scope and appear only where a design pattern is cited; figures are vendor numbers from the sources listed in the file, as of 2026-11; "announced" marks parts not yet shipping. No device has run rustinfer.

Targets

architecture string hardware backend crate state at f039b4d release
cpu any host rustinfer-target CpuTarget in the code: every R1 operator as f32 reference functions, a catalog of one cpu.<operator> kernel per compute operator, one device with a 16 GiB default budget, the oracle of every other target (RI-TGT-003) R1 (operators), R2 (collectives)
gfx942 MI300X, MI308X, MI325X rustinfer-target-rocm, feature rocm RocmTarget stub: empty catalog, no device; issue #12 binds HIP R1
gfx950 MI350X, MI355X same same R1; the reference architecture for autotuning and benchmarks (OI-008)
CDNA successor (gfx1250 class, the inventory's guess) MI450, MI455X in Helios same, when available — not in a release tag
spirv-vulkan Imagination BXM-4-64 on the SpacemiT K3 rustinfer-target-spirv-vulkan SpirvVulkanTarget stub R2 lowering, compile-tested
riscv-vector SpacemiT K3 X100 cores (RVA23, RVV 1.0), SpacemiT V100 rustinfer-target-riscv-vector RiscvVectorTarget stub R3 lowering, compile-tested; first device bring-up R3
riscv-mesh Tenstorrent Blackhole (120 Tensix cores plus 16 RISC-V Linux cores) rustinfer-target-riscv-mesh RiscvMeshTarget stub R4

In the code, a stub implements Target with an EmptyCatalog and no device: it compiles on every host, registers its string through one entry(), any kernel request fails with catalog empty naming the target (RI-RV-002) and device(0) with NoDevice. The command's registry lists exactly the six strings above and build and tune resolve --target through it before any component runs (RI-TGT-001, -004); a product name or an unregistered string is refused listing the registered ones. The rest of this section is specified in the SRS for #12: the ROCm runtime is libamdhip64 through one FFI module, with every HIP error carried as a typed error, the architecture read from gcnArchName and a mismatched artifact refused, code objects loaded only after the artifact check with each kernel's LDS and register needs checked against the device before its first launch (RI-ROC-001 to -004). ROCm 7.0 to 7.2 is the stated range. RISC-V targets go through their vendor runtime: TT-Metal for Tensix, the host OS for vector cores, Vulkan for SPIR-V devices.

class parts memory per device compute the door rustinfer uses
AMD Instinct, CDNA3 MI300X (192 GB HBM3, 5.3 TB/s, 304 CU), MI308X (binned), MI325X (256 GB HBM3E, 6 TB/s) 192 to 256 GB ~1.3 PF FP16 dense; FNUZ fp8, no fp4 HIP runtime; MLIR to ROCDL, gfx942
AMD Instinct, CDNA4 MI350X, MI355X (288 GB HBM3E, 8 TB/s, 256 CU) 288 GB 2.3 PF FP16; fp4 and fp6 matrix cores; OCP fp8 gfx950
AMD Instinct, next (announced) MI450, MI455X (432 GB HBM4) in Helios 432 GB 40 PF FP4 the CDNA successor

The inventory calls these the only RISC-V accelerators with an MLIR or LLVM door
RISC-V vector CPUs as accelerators SpacemiT K3 X100 cores, SpacemiT V100 (46 cores, server) DDR tens of TOPS; the K3's 60 TOPS INT4 NPU is closed LLVM RISC-V with RVV; the matrix extensions (IME, AME) not yet usable through LLVM intrinsics
Vulkan-class GPU on a RISC-V SoC Imagination BXM-4-64 on the K3 shared LPDDR ~1 TOPS class SPIR-V through Vulkan or OpenCL
decode-oriented accelerators, pattern only d-Matrix Corsair, Cerebras WSE-3 SRAM plus DRAM decode-bound not targets; they establish prefill on one device class and decode on another

Host CPUs

part cores memory I/O
AMD EPYC Turin (9005) up to 192 Zen 5c 12-channel DDR5-6000, 614 GB/s 128 PCIe Gen5 lanes, CXL 1.1; eight GPUs per socket
AMD EPYC Venice (2026, Zen 6) up to 256 1.6 TB/s; twice Turin's CPU-to-GPU bandwidth the Helios host, one per four MI455X
SpacemiT V100 46 RISC-V cores DDR a RISC-V host for RISC-V accelerators

What runs on the host today, per the inventory: request ingress, tokenization, detokenization, scheduling, sampling post-processing, KV block management, logging. The host is also the first offload target of the planner.

Interconnects

fabric bandwidth domain
AMD Infinity Fabric (XGMI) ~1 TB/s class aggregate per GPU across an 8-GPU node node of 8 (MI300X, MI355X)
UALink 1.0 (2025-04), 2.0 (2026-04) 200 Gb/s per lane rack; open, with AMD, Broadcom, Intel, Meta, Microsoft among the members
UALink over Ethernet in Helios 260 TB/s bidirectional per rack of 72 MI455X rack
PCIe Gen5 x16, Gen6 x16 128 GB/s, 256 GB/s host to device
Broadcom Tomahawk 6, co-packaged optics 102.4 Tb/s per chip scale-out Ethernet, UEC fabrics

On today's AMD nodes the collective path the inventory describes is an IPC all-reduce for small messages and RCCL over XGMI otherwise; on Helios, RCCL over UALoE. No in-network reduction exists on the open Ethernet side yet.

What is not on the bench

OI-003 records that no RISC-V accelerator is available and the lowering paths are chosen from documentation, with the resolution to acquire a Tenstorrent p150 and a SpacemiT K3 board before R3. OI-008 records that autotuning and the performance baselines need a gfx950 host with vLLM and AITER. OI-010 defers the DPU agent until a DPU is on the bench.
