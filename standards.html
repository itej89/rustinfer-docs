Standards map

rustinfer reads and writes formats it did not invent: safetensors shards, OCP microscaling blocks, AMD code objects, JSON sections, later an OpenAI-shaped HTTP API. SRS §1.4 marks each reference it names: mandatory R when a requirement can be met only by conforming to it, from release n; process, informative or internal otherwise. This map shows the mandatory ones, by area. A standard is never met as a whole: rustinfer conforms to the parts in its scope, the scope its §1.4 row names, and each standard's requirements page lists those parts one by one.

Two separate things are shown for each standard. The colour is its state, from its audit:

  • works: every in-scope item conforms on main; open gaps, if any, are in the tests, not the behaviour;
  • partly works: some in-scope items conform, others are missing or wait in an open pull request;
  • missing: nothing in scope conforms on main yet;
  • later release: the standard is mandatory only from a release after the current one, so nothing is due yet; the work is recorded on its tracker.

The assessed tag appears when the standard has an audit page, dated, that checks the implementation item by item against the specification's own text, downloaded into the site's specs/ folder (not published). Where the specification is sold and could not be read (IEEE 754, ISO 8601), the tag adds secondary: the audit used the named public sources its requirements page lists instead.

Each standard has four pages: the overview (what it is, its scope and how far rustinfer meets it), the requirements (what the specification asks, in scope), the audit (each requirement against the code, with the evidence and its date) and the tracker (the gaps). A gap is open when its status is Open or In PR #N; a Later release R gap is recorded but not counted as open; an Out of scope gap, one the owner removed from the §1.4 scope (OCP OFP8's non-saturating mode, PR #50), is kept for the record and counted nowhere. The same counts feed the issue tracker and the progress page. The standards diagram of the architecture diagram places the same standards on the parts of rustinfer that implement them, and the show standards switch puts them on each C4 level.

SRS §1.4 also names documents that are not standards rustinfer must conform to: process (how the project is developed), informative (background, method, evidence) and internal (the project's own decisions, on the decisions page). None has a tracker.

How a standard is added

  1. A row in SRS §1.4 through an SRS amendment: the ID, the exact title, the pinned version and its date, the scope, and the conformance mandatory R<n>. The version is the one the code is written against; "latest" is not a pin.
  2. Its four pages, content/std-<id>.md, -requirements, -audit and -tracker, with section: Standards, group: "<Area> / <Name> <version>" and four consecutive orders; the specification downloaded into specs/.
  3. Its record, data/standards/<id>.json: name, version, area, conformance, state, whether it is assessed, the audit date and the source of the specification (downloaded or secondary).
  4. .venv/bin/python scripts/reference/gen_standards.py, which checks the pages against the record and the SRS, recomputes the gap counts from the tracker and rewrites the map above.
