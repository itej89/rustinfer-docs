Lessons from vLLM, SGLang and TensorRT-LLM

Read from docs/planning/trt-llm-feature-inventory.md, the rationale lines of the SRS, and the context sections of ADR-005 and ADR-006 at commit 082df51. The inventory was read from NVIDIA's documentation on 2026-11-10; rows it could not source from documentation are marked in the file as coming from the executor API headers as known to the author. The vLLM and SGLang lessons are the ones the SRS states as rationale; this page does not add others.

The lesson that shaped the whole engine

TensorRT-LLM has two runtimes. The classic engine flow (convert_checkpoint → trtllm-build → rank{N}.engine → the C++ executor) fixes every kernel, fusion, precision choice and memory plan at build time under optimization profiles. NVIDIA now marks it legacy and recommends the PyTorch backend, where the graph is Python, kernels are selected at run time and CUDA graphs capture the decode step. The inventory's reading of why: a rebuilt engine per profile, per GPU and per TensorRT version was too rigid for the pace of model releases.

rustinfer keeps the ahead-of-time engine, which was the owner's requirement, and takes the lesson in two ways:

  • The artifact is semi-static. Batch size, token count and sequence lengths are profile-bounded run-time values; graph, fusion, precision, kernel choice, layouts, arena plan and KV geometry are fixed at build. A rebuild is needed for a new model, target, precision or profile range, never for a new batch shape.
  • The artifact is a cache (ADR-006). TensorRT-LLM removed its mandatory build step in version 1.2; vLLM and SGLang compile and capture on first load and cache the result. What is worth keeping is the artifact's properties, not the obligation to run a command first; so run and serve build on first load, and --require-prebuilt restores the obligation for fleets that want it.

What the SRS takes from vLLM and SGLang

Each of these appears as the rationale of a requirement.

lesson requirement the SRS's words
vLLM V1's block pool RI-KVC-002: O(1) allocation and release from one pre-allocated pool with an LRU free list "prefix reuse must cost nothing at a 0 percent hit rate"
vLLM V1's uniform scheduler RI-SCH-010: one token-level model for prefill, chunked prefill, decode, reuse and speculation "features compose when the scheduler is uniform"
vLLM V1 and SGLang on host overhead RI-NFR-004: under 500 µs host time per iteration at batch 64 with the overlap scheduler off "host overhead is the bottleneck as GPUs get faster"
SGLang's RadixAttention RI-KVC-005: filled blocks indexed by token prefix in a radix tree, reuse on by default "agent traffic served well by default"
Both engines' first-load compilation ADR-006 the artifact is a cache
Python on the serving path ADR-005's context it "would reintroduce the host overhead vLLM V1 and SGLang spent a year removing"

What the incumbents do not have

The inventory's last section: a target other than NVIDIA, and its own kernels. TensorRT-LLM's kernels are NVIDIA's; vLLM and SGLang on AMD run on AITER's. rustinfer generates every kernel from its Kernel IR and keeps its own catalog per target, which is the premise of ADR-005 and the reason the kernel compiler exists. AITER remains the benchmark baseline (RI-NFR-003, RI-NFR-006) and the SRS lists the AITER documentation site in its references for that purpose.
